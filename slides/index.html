Where we started

A database was doing a search engine's job

MySQL full-text search answers one question: does this row contain these words?

Yes or no — so there is no “better match,” and nothing meaningful to rank by.
No vocabulary. pnf is three letters, not an abbreviation for plexiform neurofibroma.
Every column counts the same. A stray word in a usage note beats an exact resource name.
Any change to how text is handled means a schema change and a migration.
Recorded on the legacy search · SME benchmarking spreadsheet
pnf0 results · plexiform neurofibroma lines exist
cnf0 results · cutaneous neurofibroma lines exist
neurofibromin0 results · ~100 antibodies in the registry
nf1-flox0 results · ~100 flox models in the registry
Four of the twenty SME phrases returned nothing at all. The data was always there — the search could not reach it.

testing

Setting the cell-line category column to exact-label reading looked sensible. But exact also means case-sensitive — and users type lowercase, so the query returned nothing at all. The benchmark caught it in testing, before release; we reverted that column to prose reading.

Live weights on the nf-studies index · benchmark/studies/fields.yaml

What the weights buy

The default gives every column an equal vote. So a study whose summary happens to mention “therapy” can outrank a study whose tumour-type field actually says schwannoma.

Why only 3 of 17 columns?

The rest are configured as exact, case-sensitive labels for filtering — NTAP returns 101 studies, ntap returns 0. Users type lowercase, so those columns could never contribute. Removing them improved the results. We only knew because we measured.

Being straight about it

What is still hard — and who can fix it

5 of the 48 tool searches still fail outright. They fail for three different reasons, and the reasons have three different owners.

Ours · query shape

Generic words drown out specific ones

Adding two common words to a good query buries the right answers. Not a weighting problem — we tested that, and it made it worse.

melanoma cell line
“melanoma” alone → ranks 1 and 4
+ “cell line” → 16 and off the page
Curation · not search

The information was never recorded

Café-au-lait spots are a hallmark NF1 sign and the models do show it — but no model row carries that annotation. Search cannot find what nobody wrote down.

café-au-lait spots · nf1 metabolic model
an annotation gap surfacing as a search gap
Frontend · blocked on us

The improvements aren't reaching users yet

The portal sends a bare, unweighted query with typo tolerance hard-coded on. Field weights, query shape and fuzziness are not adjustable from configuration.

Measured but not shipped
every gain in slide 9's right column is waiting
The ask

One frontend change unlocks the measured gains: let the portal send a field list, per-field weights, a query shape and a fuzziness setting instead of hard-coding them. Then tuning becomes a configuration decision we can make and measure — per index, per portal — without shipping software each time.

Where this leaves us

Real work, measurable benefit

For researchers

Search the way you actually talk — abbreviations, shorthand, partial clone names, a disease term instead of a resource name. All of that used to return nothing.

For the programme

Improvements are proven, not asserted. Every claim has a command behind it and a golden set holding it honest.

For the team

Tuning is a config file and a benchmark run, not a project. New index, new golden set, tuner run, reviewed recommendation.

If you remember one number: with the settings we have already measured, all 31 of 31 expert searches on the studies catalogue return something useful on page one. Today it is five in six — and the only thing in between is the one change on the previous slide.
